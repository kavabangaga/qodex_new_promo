# Как сайт попадает на qodex.tech

Коротко: **push в ветку `main` этого репозитория → GitHub сам собирает сайт и выкладывает его на qodex.tech**
(3–5 минут). Push в `dev` — только сборка и проверка, на сервер ничего не уходит. Руками на сервер ничего
копировать не нужно.

## Ветки

| Ветка  | Что происходит после push                                    |
|--------|--------------------------------------------------------------|
| `dev`  | сборка и проверки; сайт на сервере не меняется                |
| `main` | сборка, проверки и **выкладка на https://qodex.tech**         |

Работаем в `dev`. Когда правка проверена — переносим её в `main` (`git push origin dev:main` или pull request
`dev` → `main`).

## Что происходит после push в `main`

Всё делает GitHub Actions — сценарий «Выкладка на боевой» (`.github/workflows/deploy-prod.yml`):

1. **Сборка.** Сайт из папки `version4/` (Astro) собирается для адреса https://qodex.tech.
2. **Проверка сборки.** На месте ли страницы, страница 404, документы, отправляет ли форма заявку на `/api/request`.
3. **Передача на сервер.** Архив с контрольными суммами уходит по SSH на сервер qodex.tech. Ключ выкладки хранится
   в GitHub (Settings → Environments → `production`) и умеет только одно — запустить приёмник версий;
   войти на сервер по нему нельзя.
4. **Переключение без простоя.** Приёмник проверяет архив, кладёт его в новую папку
   `/opt/qodex-site/releases/<время коммита>-<коммит>` и мгновенно переключает на неё сайт
   (ссылка `/opt/qodex-site/current`). На сервере хранятся 5 последних версий.
5. **Проверка снаружи.** GitHub открывает https://qodex.tech и сверяет номер версии на странице
   (`<meta name="qodex-build">`). Если там не новая версия — сам возвращает предыдущую и помечает запуск ошибкой.

Итог смотрите в **Actions → «Выкладка на боевой»**: зелёный запуск — новая версия уже на сайте.

## Посмотреть версии или откатить

**Actions → «Выкладка на боевой» → Run workflow**, ветка `main`, в поле действия:

- `status` — какие версии лежат на сервере и какая сейчас на сайте;
- `rollback` — вернуть предыдущую версию (или указать нужную в поле «Номер версии»);
- `deploy` — заново собрать и выложить `main`.

Чтобы отменить правку, сделайте `git revert` и обычный push в `main`. Не делайте force-push `main` на старый
коммит: сервер не примет версию старше той, что уже на сайте.

## Куда уходят заявки с сайта

Форма отправляет заявку на `https://qodex.tech/api/request`, и дальше она идёт двумя путями:

- **письмо на info@qodex.tech** — служба `mail.service` на сервере (`/opt/mail-sender`, не из этого репозитория);
- **карточка в CRM Weeek** — веб-сервер копирует заявку службе `qodex-weeek-bridge` (`server/weeek-bridge/`),
  та заводит сделку в воронке «Сайт qodex.tech» с тегами отмеченных продуктов.

## Что НЕ выкладывается автоматически

Эти части лежат в репозитории, но на сервер ставятся вручную, по инструкции в своей папке:

| Что                                     | Где в репозитории                    | Инструкция                       |
|-----------------------------------------|--------------------------------------|----------------------------------|
| Настройки веб-сервера qodex.tech (nginx): сайт, перенаправления, приём заявок | `deploy/nginx/` | `deploy/README.md` |
| Приёмник версий на сервере              | `deploy/server/qodex-release`        | `deploy/README.md`               |
| Передача заявок в CRM Weeek             | `server/weeek-bridge/`               | `server/weeek-bridge/README.md`  |

`server/lead-mailer/` — запасной вариант, не используется.

## Нельзя

- Править файлы в `/opt/qodex-site` на сервере руками — следующая выкладка их заменит, а в истории правки не будет.
- Класть в репозиторий ключи, пароли и токены: они хранятся в настройках GitHub и в закрытых файлах на сервере.

Подробнее (устройство сервера, разовая настройка, проверки) — [`deploy/README.md`](deploy/README.md).
