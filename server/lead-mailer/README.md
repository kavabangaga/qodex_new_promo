# Приёмник заявок с сайта qodex.tech (lead-mailer)

Для администратора сервера, на котором работает qodex.tech.

## Что он делает

Посетитель заполняет форму на сайте (имя, телефон, какие продукты интересны, галочка согласия) и нажимает
«Отправить заявку». Дальше:

1. Браузер отправляет заявку на `https://qodex.tech/api/lead` (POST, JSON).
2. nginx передаёт запрос программе `lead_mailer.py`, которая слушает только `127.0.0.1:8787` (снаружи недоступна).
3. Программа проверяет поля и отправляет заявку **одним письмом на info@qodex.tech** через почтовый сервер
   Mail.ru / VK WorkSpace (`smtp.mail.ru:465`, SSL), от имени ящика из настроек.
4. Только после того как почтовый сервер принял письмо, сайт показывает «Спасибо». Если письмо не ушло,
   посетитель видит сообщение «Не получилось отправить заявку. Позвоните … или напишите на info@qodex.tech».
5. После отправки письма программа дописывает **запись о согласии** на обработку персональных данных
   в файл `/var/lib/qodex-lead/consent.jsonl`. Это доказательство согласия (ч. 3 ст. 9 152-ФЗ). По тексту
   согласия на сайте (пункты 5.2 и 6.5) запись хранится три года, потом удаляется. Раз в месяц это делает
   задание cron (шаг 6). Перед отправкой программа проверяет, что запись получится сохранить. Если файл
   недоступен или на диске меньше 1 МБ, письмо не отправляется, посетитель видит ту же ошибку, а в журнале
   появляется строка `ОШИБКА: CONSENT_LOG недоступен`. Письмо не может заменить запись: его удаляют
   не позже чем через 30 дней.

Письмо выглядит так:

```
Тема: Заявка с сайта qodex.tech: РО-БОТ, QODEX Tracker

Имя: Иван Петров
Телефон: +79991234567 (введено: +7 (999) 123-45-67)
Интересует: РО-БОТ, QODEX Tracker
Tracker: запрос демо (пилот не обещаем)
Страница: https://qodex.tech/tracker/
UTM: utm_source=yandex; utm_campaign=autumn
Отправлено: 09.10.2026 12:34:56 МСК (время браузера)
Получено: 09.10.2026 12:34:57 МСК / 09.10.2026 09:34:57 UTC (время сервера)
Согласие на обработку персональных данных: дано, редакция от 09.10.2026, текст: https://qodex.tech/consent/
```

Если продукт не отмечен, тема заканчивается словами «продукт не выбран».

Телефон принимается в том виде, в каком его пропускает форма: с добавочным («8 (999) 123-45-67 доб. 5»,
«#12», «ext 5»), с любыми тире, с подписью после номера. В письме он выглядит так:
`Телефон: +79991234567 доб. 5 (введено: 8 (999) 123-45-67 доб. 5)`. Отклоняется только строка, где нет
номера из 10–15 цифр.

Что ещё важно знать:

- Данные заявки остаются на этом сервере и в почте qodex.tech. Сторонних сервисов, библиотек и пакетов нет:
  только стандартный Python 3.8 или новее.
- Защита от потока заявок, в три уровня (дальше ответ 429):
  - nginx: с одного адреса 6 запросов подряд, потом один в 30 секунд;
  - программа: не больше 5 принятых заявок за 10 минут с одного адреса IPv4 или с одной сети IPv6 /64
    (обычный компьютер с IPv6 владеет целой /64 и мог бы менять адрес на каждую заявку);
  - общий потолок: 30 принятых заявок в час со всех адресов вместе (`MAX_LEADS_PER_HOUR`). Он нужен,
    чтобы через форму нельзя было рассылать спам от имени ящика компании.
- Тело запроса не больше 16 КБ. Принимается только `Content-Type: application/json`, поэтому чужой сайт
  не отправит заявку из браузера посетителя. Текст, который ввёл посетитель, в заголовки письма не попадает,
  а переводы строк и управляющие символы из него удаляются.
- В журнал (journald) пишутся только строки состояния вида `POST /api/lead 200 заявка отправлена`.
  Имён, телефонов и IP-адресов в журнале нет.
- Пароль от почты лежит только в файле окружения службы (`/etc/qodex/lead-mailer.env`, права 600). В коде
  паролей нет.

## Что нужно заранее

- Linux с systemd и nginx, Python 3.8 или новее: `python3 --version` (в Debian 12 — 3.11).
- Ящик на домене qodex.tech, от имени которого будут уходить письма. По умолчанию это отдельный ящик
  `site@qodex.tech`, его нужно завести в VK WorkSpace. Тогда на сервере не хранится пароль от основного ящика,
  а если кто-то попробует завалить форму заявками, почтовый сервис ограничит отправку с `site@`, а не
  с `info@`. Если отдельный ящик заводить не стали, можно указать `info@qodex.tech`.
- С сервера должны открываться исходящие соединения на `smtp.mail.ru:465`. Некоторые хостинги закрывают
  почтовые порты. Проверка:

  ```bash
  echo QUIT | timeout 15 openssl s_client -connect smtp.mail.ru:465 -crlf -quiet
  ```

  Должны появиться строки, которые начинаются с `220` и `221`. Если их нет и команда завершилась
  по таймауту, попросите хостинг открыть исходящий порт 465.

## Установка

Команды выполняются от root из папки, куда скопированы файлы. Если вы вошли не как root, добавляйте `sudo`
в начале команд или выполните сначала `su -`. На минимальном Debian `sudo` может не быть, поэтому ниже,
где нужно действовать от имени службы, используется `runuser`.

### 1. Пользователь и программа

```bash
useradd --system --no-create-home --home-dir /nonexistent --shell /usr/sbin/nologin qodex-lead
install -d -m 0755 /opt/qodex-lead-mailer
install -m 0644 lead_mailer.py /opt/qodex-lead-mailer/lead_mailer.py
```

### 2. Пароль для внешнего приложения

Обычный пароль от почты программе не нужен и не подходит. Нужен **пароль для внешнего приложения**:

1. Администратор сервера сам входит в ящик (`SMTP_USER`, например `site@qodex.tech`) в веб-почте Mail.ru.
2. Открывает настройки: «Безопасность» → «Пароли для внешних приложений» и создаёт пароль, например
   с названием «Сайт qodex.tech». Названия пунктов в интерфейсе могут немного отличаться. Если такого пункта нет,
   администратор домена в панели VK WorkSpace разрешает доступ к почте из внешних программ.
3. Сразу вписывает пароль в файл на сервере (шаг 3).

Пароль никому не пересылают: ни в чатах, ни в мессенджерах, ни в письмах. Если он попал в переписку,
удалите его в настройках ящика и создайте новый.

### 3. Файл настроек

```bash
install -d -m 0750 /etc/qodex
install -m 0600 -o root -g root lead-mailer.env.example /etc/qodex/lead-mailer.env
nano /etc/qodex/lead-mailer.env
```

В файле проверить `SMTP_USER` (ящик целиком, с `@qodex.tech`; по умолчанию `site@qodex.tech`) и заполнить
`SMTP_PASSWORD` (пароль из шага 2), без кавычек. Остальное оставить как есть: письма уходят
на `MAIL_TO=info@qodex.tech`.

### 4. Служба

```bash
install -m 0644 qodex-lead-mailer.service /etc/systemd/system/qodex-lead-mailer.service
systemctl daemon-reload
systemctl enable --now qodex-lead-mailer
systemctl status qodex-lead-mailer
```

В статусе должно быть `active (running)`, а в журнале — строка `lead-mailer: запущен: 127.0.0.1:8787, …`.
Если в настройках нет пароля или ящика, служба сразу остановится и напишет в журнал, чего не хватает.

Порт 8787 занят? Поменяйте `PORT` в `/etc/qodex/lead-mailer.env` и порт в строке `proxy_pass`
в рабочей копии сниппета `/etc/nginx/snippets/qodex-api-lead.conf` (шаг 5), затем:

```bash
nginx -t && systemctl reload nginx && systemctl restart qodex-lead-mailer
```

### 5. nginx

```bash
install -D -m 0644 nginx-api-lead.conf /etc/nginx/snippets/qodex-api-lead.conf
install -D -m 0644 nginx-lead-limit.conf /etc/nginx/conf.d/qodex-lead-limit.conf
```

`install -D` создаёт папку, если её нет: в пакетах nginx.org папки `/etc/nginx/snippets` нет. Второй файл
описывает зону ограничения частоты и должен попасть в контекст `http { }`. В Debian и в пакетах nginx.org
файлы `/etc/nginx/conf.d/*.conf` подключаются именно туда. Проверка: `grep conf.d /etc/nginx/nginx.conf`.
Если строки нет, перенесите строку `limit_req_zone …` из этого файла прямо в `http { }` файла
`/etc/nginx/nginx.conf`.

В блок `server { … }` сайта qodex.tech, который отвечает по https (порт 443), добавить строку:

```nginx
include /etc/nginx/snippets/qodex-api-lead.conf;
```

Ту же строку нужно добавить в каждый другой `server { … }`, который отдаёт сайт. Например, в блок для
`www.qodex.tech`, если он показывает сайт, а не перенаправляет на `qodex.tech`.

Затем:

```bash
nginx -t && systemctl reload nginx
```

Если перед nginx стоит ещё один прокси или защита от DDoS, `$remote_addr` будет адресом этого прокси,
и лимит «5 заявок за 10 минут» станет общим на всех. Тогда nginx должен получать настоящий адрес
посетителя (модуль `realip`).

### 6. Ежемесячное удаление старых записей о согласии

Записи старше 1095 дней (три года) удаляются раз в месяц, 1-го числа в 04:30, от имени пользователя службы:

```bash
cat > /etc/cron.d/qodex-lead-purge <<'EOF'
# QODEX: удалять записи о согласии старше трёх лет (п. 6.5 согласия на сайте)
30 4 1 * * qodex-lead /usr/bin/python3 -I /opt/qodex-lead-mailer/lead_mailer.py --purge-older-than-days 1095 2>&1 | /usr/bin/logger -t qodex-lead-purge
EOF
chmod 0644 /etc/cron.d/qodex-lead-purge
```

Имя файла в `/etc/cron.d` — без точки, иначе cron его пропустит. Если cron не установлен:
`apt install cron`.

Если `CONSENT_LOG` в настройках перенесли в другую папку:

1. Добавьте эту папку в строку `ReadWritePaths=` в `/etc/systemd/system/qodex-lead-mailer.service`
   (например, `ReadWritePaths=/var/lib/qodex-lead /новая/папка`) и выполните
   `systemctl daemon-reload && systemctl restart qodex-lead-mailer`. Служба видит файловую систему только
   для чтения, кроме перечисленных папок, и без этой строки не запустится.
2. Добавьте в начало файла cron строку `CONSENT_LOG=/новый/путь/consent.jsonl`.

Проверить вручную и посмотреть результат:

```bash
runuser -u qodex-lead -- /usr/bin/python3 -I /opt/qodex-lead-mailer/lead_mailer.py --purge-older-than-days 1095
journalctl -t qodex-lead-purge
```

Программа пишет только количество: `удалено N, осталось M`.

## Проверка

Журнал службы:

```bash
journalctl -u qodex-lead-mailer -f
```

Пробная заявка прямо на сервере (минуя nginx), а затем через сайт:

```bash
curl -i http://127.0.0.1:8787/api/lead \
  -H 'Content-Type: application/json' \
  --data '{"name":"Проверка","phone":"+7 900 000-00-00","interest":["tonn"],"trackerDemo":false,"utm":{},"page":"https://qodex.tech/","sentAt":"2026-10-09T09:00:00Z","consent":{"given":true,"edition":"09.10.2026","text":"https://qodex.tech/consent/"}}'

curl -i https://qodex.tech/api/lead \
  -H 'Content-Type: application/json' \
  --data '{"name":"Проверка через сайт","phone":"+7 900 000-00-00","interest":[],"trackerDemo":false,"utm":{},"page":"https://qodex.tech/","sentAt":"2026-10-09T09:00:00Z","consent":{"given":true,"edition":"09.10.2026","text":"https://qodex.tech/consent/"}}'
```

Ответ `HTTP/1.1 200` и `{"ok": true}`, на info@qodex.tech приходит письмо «Заявка с сайта qodex.tech: …».
Пробные заявки оставляют в файле записей о согласии строки с вымышленным номером `+79000000000`. Они удалятся
вместе с остальными через три года. Править файл вручную не нужно: служба дописывает его прямо сейчас.

После выкладки сайта отправьте заявку из настоящей формы на qodex.tech.

Ответы приёмника:

| Код | Что значит |
| --- | --- |
| 200 `{"ok": true}` | письмо принято почтовым сервером, запись о согласии сохранена |
| 400 | поле не прошло проверку; в ответе название поля: `name`, `phone`, `interest`, `consent`, `json`, `body` |
| 404 / 405 | не тот адрес / не POST (nginx на не-POST сам отвечает 403) |
| 408 | тело запроса не пришло за 30 секунд |
| 411 / 413 / 415 | нет длины тела / тело больше 16 КБ / не `application/json` |
| 429 | слишком часто: больше 5 заявок за 10 минут с одного адреса, или общий потолок в час (в журнале — `общий лимит`), или ограничение nginx |
| 502 `{"ok": false}` | почтовый сервер не принял письмо; запись о согласии в этом случае не сохраняется |
| 503 `{"ok": false}` | запись о согласии сохранить нельзя, поэтому письмо не отправлялось (в журнале — `ОШИБКА: CONSENT_LOG недоступен`) |

При 502 в журнале видна причина, например:

- `SMTPAuthenticationError 535`: неверный ящик или пароль для внешнего приложения (шаг 2);
- `ConnectionRefusedError`, `TimeoutError`, `gaierror`: сервер не может соединиться с `smtp.mail.ru:465`
  (см. «Что нужно заранее»). На каждое действие с почтовым сервером программа ждёт 10 секунд.

**Ежедневная проверка.** Раз в день (или в вашей системе мониторинга) смотрите, нет ли ошибок:

```bash
journalctl -u qodex-lead-mailer --since yesterday | grep ОШИБКА
```

- `ОШИБКА: CONSENT_LOG недоступен`: заявки сейчас **не принимаются** (посетители видят ошибку). Проверьте
  права на `/var/lib/qodex-lead` (владелец `qodex-lead`, права 700), владельца файла `consent.jsonl`
  и место на диске (`df -h /var/lib/qodex-lead`). Как только запись снова возможна, заявки принимаются
  без перезапуска.
- `ОШИБКА: запись о согласии не сохранена`: редкий случай, когда запись не удалась уже после отправки
  письма (например, диск заполнился в эту секунду). Письмо ушло, но записи о согласии по этой заявке нет.
  Устраните причину и сохраните письмо этой заявки отдельно, пока не пройдут три года.

Строка `общий лимит` означает, что за час пришло больше 30 заявок. Если это настоящие заявки, а не спам,
поднимите `MAX_LEADS_PER_HOUR` в `/etc/qodex/lead-mailer.env` и выполните
`systemctl restart qodex-lead-mailer`.

## Сборка сайта для qodex.tech

Сайт собирается на компьютере разработчика (или на сервере, если там есть Node.js 22.12 или новее)
из папки `version4` репозитория:

```bash
cd version4
npm ci
SITE_URL=https://qodex.tech SITE_BASE=/ PUBLIC_FORM_ENDPOINT=/api/lead npm run build
```

То же в PowerShell (Windows):

```powershell
cd version4
npm ci
$env:SITE_URL='https://qodex.tech'; $env:SITE_BASE='/'; $env:PUBLIC_FORM_ENDPOINT='/api/lead'; npm run build
```

**Без `PUBLIC_FORM_ENDPOINT=/api/lead` форма только изображает отправку, и заявки теряются.** Проверка сборки:

```bash
grep -c 'data-endpoint="/api/lead"' dist/index.html
```

Должно быть число больше нуля.

Готовый сайт лежит в `version4/dist/`.

**Первая выкладка.** Сейчас из корневой папки qodex.tech работает старый сайт. Новый сайт кладут
в **отдельную** папку и переключают на неё nginx. Старую папку не трогают: она и есть откат.

```bash
# на компьютере разработчика: новая папка рядом со старой
rsync -a version4/dist/ user@server:/var/www/qodex.tech-v4/

# на сервере: перенести файлы подтверждения Яндекс Вебмастера и Google Search Console из старой папки
# (старая папка — та, что сейчас указана в строке root блока server { } сайта; здесь /var/www/qodex.tech)
cp -a /var/www/qodex.tech/yandex_*.html /var/www/qodex.tech/google*.html /var/www/qodex.tech-v4/ 2>/dev/null
```

Если в старой папке есть и другие файлы, которые положили вручную и на которые ведут ссылки снаружи
(например, документы), их тоже нужно перенести. Потом в блоке `server { … }` сайта qodex.tech в nginx:

```nginx
root /var/www/qodex.tech-v4;
index index.html;

location / {
    try_files $uri $uri/ =404;
}
error_page 404 /404.html;

include /etc/nginx/snippets/qodex-api-lead.conf;
```

```bash
nginx -t && systemctl reload nginx
```

**Откат:** вернуть прежнюю строку `root` и выполнить `nginx -t && systemctl reload nginx`. Старую папку
не удаляйте, пока новый сайт не проработает хотя бы несколько недель.

**После переключения** откройте старые адреса, на которые есть внешние ссылки. В первую очередь это
страница `/documents` и файлы документов, на которые ссылается реестр российского ПО (Минцифры),
а также адреса из поиска Яндекса. Если адрес изменился, добавьте в `server { … }` переадресацию,
например `location = /старый-адрес { return 301 /новый-адрес/; }`.

**Следующие выкладки** идут в ту же папку. `--delete` убирает файлы прошлой сборки, а `--exclude`
защищает файлы подтверждения. Всё остальное, чего нет в сборке, `--delete` удалит. Поэтому файлы,
перенесённые вручную при первой выкладке, нужно положить в `version4/public/`, чтобы они попадали в сборку,
или добавить для каждого свой `--exclude`. Перед выкладкой сделайте копию для отката:

```bash
# на сервере
rm -rf /var/www/qodex.tech-v4.prev && cp -a /var/www/qodex.tech-v4 /var/www/qodex.tech-v4.prev
# на компьютере разработчика
rsync -a --delete --exclude='yandex_*.html' --exclude='google*.html' version4/dist/ user@server:/var/www/qodex.tech-v4/
```

Откат такой выкладки: `rm -rf /var/www/qodex.tech-v4 && mv /var/www/qodex.tech-v4.prev /var/www/qodex.tech-v4`.

## Перед тем как включить форму

**Согласие должно называть обработчиков.** Сейчас в разделе 4 согласия (`/consent/`, файл
`version4/src/pages/consent.astro`) сказано, что наименования и адреса обработчиков Оператор сообщает
по запросу. По ч. 4 ст. 9 152-ФЗ в согласии нужно указать наименование и адрес лица, которое обрабатывает
данные по поручению Оператора. Для этой схемы это:

- хостинг-провайдер сервера, на котором работают сайт и приёмник;
- почтовый сервис (Mail.ru для бизнеса / VK WorkSpace).

Полные юридические наименования и адреса даёт владелец сайта. Разработчик вписывает их в раздел 4 до запуска.
Если текст согласия изменится после 09.10.2026, нужна новая дата редакции: `CONSENT_EDITION.form`
в `version4/src/config/site.ts`. Когда подключат CRM или SMS, её тоже нужно будет назвать в согласии.

## Записи о согласии

Файл `/var/lib/qodex-lead/consent.jsonl`, одна строка на заявку:

```json
{"received_at":"2026-10-09T09:34:57Z","phone":"+79991234567","consent_given":true,"consent_edition":"09.10.2026","consent_text":"https://qodex.tech/consent/","page":"https://qodex.tech/tracker/"}
```

Время `received_at` берётся по часам сервера, в UTC. Имени в записи нет. Для подтверждения согласия по п. 6.5
нужны дата и время, редакция согласия и номер телефона; адрес текста согласия и страница формы
уточняют, где и какой текст человек видел. Страница записывается без строки запроса и якоря (`?…`, `#…`):
рекламные метки (utm, yclid, gclid) не хранятся рядом с телефоном три года. Они есть только в письме.
Телефон в записи — основной номер, приведённый к виду `+7…`, без добавочного.

Найти запись по номеру (например, если человек спрашивает о своих данных или отзывает согласие):

```bash
grep '"phone":"+79991234567"' /var/lib/qodex-lead/consent.jsonl
```

- Отзыв согласия приходит письмом на info@qodex.tech или по почте. По п. 6.5 его тоже хранят три года:
  сохраните письмо об отзыве (например, в отдельной папке ящика). Запись о согласии при отзыве **не удаляют**:
  она нужна, чтобы подтвердить, что согласие было.
- Если сервер копируется в резервные копии, файл попадает и туда. Копии храните в России и не дольше,
  чем нужно.
- 1095 дней cron считает от дня заявки. По п. 6.5 запись хранится три года после окончания обработки заявки.
  Обычно заявку обрабатывают за дни или недели, и разница — эти недели. Если владелец сайта решит
  считать строго по тексту согласия, число в задании cron можно увеличить (например, до 1460: три года
  плюс год на работу с заявкой).

## Письма с заявками

Письма в ящике тоже содержат персональные данные. По тексту согласия:

- письма не пересылают на зарубежную почту и в зарубежные сервисы (раздел 4);
- после того как заявка отработана или человек отозвал согласие, письмо удаляют не позже чем через 30 дней
  (п. 6.3), если нет другого законного основания хранить данные (например, заключённого договора).

Это делают сотрудники, которые работают с заявками.

## Обновление и удаление

Обновить программу:

```bash
install -m 0644 lead_mailer.py /opt/qodex-lead-mailer/lead_mailer.py
systemctl restart qodex-lead-mailer
```

Если в новой версии изменились и другие файлы, их тоже нужно поставить заново: `qodex-lead-mailer.service`
(затем `systemctl daemon-reload`), `nginx-api-lead.conf` и `nginx-lead-limit.conf` (затем
`nginx -t && systemctl reload nginx`). Свои правки в рабочих копиях (например, другой порт) перенесите.

Поменять пароль: создать новый пароль для внешнего приложения, вписать его в `/etc/qodex/lead-mailer.env`,
`systemctl restart qodex-lead-mailer`, старый пароль удалить в настройках ящика.

Удалить приёмник: `systemctl disable --now qodex-lead-mailer`, убрать строку `include` из nginx, удалить
`/etc/nginx/conf.d/qodex-lead-limit.conf`, выполнить `nginx -t && systemctl reload nginx` и удалить
`/etc/cron.d/qodex-lead-purge`. Папку `/var/lib/qodex-lead` с записями о согласии не удаляйте раньше
срока: они нужны три года.

## Локальная проверка (для разработчика)

```bash
python test_lead_mailer.py
```

Тест поднимает на 127.0.0.1 поддельный почтовый сервер, запускает приёмник с тестовыми настройками и проверяет:

- правильную заявку;
- телефоны в любом виде, который пропускает форма (добавочный, тире, подпись), и неверные телефоны;
- нет согласия, слишком большое или недосланное тело, медленную присылку тела, не JSON, не POST;
- попытку вставить заголовок через имя;
- 6-ю заявку с одного адреса, с одной сети IPv6 /64, общий потолок 30 в час, 20 и 60 одновременных заявок;
- недоступную, медленную и отклоняющую почту (502 без записи о согласии);
- отправку по SSL с проверкой сертификата (тестовый сертификат вшит в тест);
- недоступный файл записей о согласии (503, письмо не уходит);
- остановку во время отправки;
- согласованность таймаутов с nginx;
- очистку старых записей и отсутствие имён, телефонов и адресов в журнале.

Нужен только Python 3.8+. Прогон занимает около 30 секунд.
